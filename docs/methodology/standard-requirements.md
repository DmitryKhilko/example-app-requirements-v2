# Стандарт создания требований к ПО {#standard-requirements}

## Обзор {#overview}

Стандарт отвечает на один вопрос аналитика: куда записать требование и как его назвать. Правила одинаковы для любой 
функциональности. 

## Типы требований {#types}

В таблице перечислены все типы требований продукта. Для каждого типа указаны префикс, расшифровка и вид ID на трёх 
уровнях: глобальном, уровне основной функциональности (F) и уровне детальной функциональности (SF). ID строится по схеме 
`ТИП-ОБЛАСТЬ-НОМЕР`: у глобального требования области нет (`BR-028`), у требования уровня F в области стоит код 
функциональности (`BR-COUNTRY-001`), у требования уровня SF — коды функциональности и детальной функциональности 
(`FR-COUNTRY-CREATE-001`). «Нет» в ячейке означает, что требование этого типа на данном уровне не записывается, 
«встраивается в FR» — что оно оформляется условием внутри функционального требования. Код `COUNTRY` в примерах — код 
основной функциональности «Справочник стран».

| Префикс | Расшифровка | Глобальный | Уровень F | Уровень SF |
|---|---|---|---|---|
| **BG** | Business Goal, бизнес-цель | `BG-001` | нет | нет |
| **CON** | Constraint, проектное ограничение | `CON-001` | `CON-COUNTRY-001` (только если ограничение касается одной F) | нет |
| **BR** | Business Rule, бизнес-правило | `BR-028` | `BR-COUNTRY-001` | встраивается в FR |
| **F** | Feature, основная функциональность | нет | `F-COUNTRY` | нет |
| **SF** | Sub-Feature, детальная функциональность | `SF-G-PAG` | нет | `SF-COUNTRY-CREATE` |
| **UC** | Use Case, сценарий достижения цели | нет | `UC-COUNTRY-001` | нет |
| **FR** | Functional Requirement, функциональное требование | `FR-G-PAG-001` (только внутри глобальной SF) | `FR-COUNTRY-001` | `FR-COUNTRY-CREATE-001` |
| **NFR** | Non-Functional Requirement, характеристика качества | `NFR-001` | `NFR-COUNTRY-001` | встраивается в FR или отдельно, если есть собственный показатель |
| **DR** | Data Requirement, требование к данным | `DR-001` | `DR-COUNTRY-001` | `DR-COUNTRY-UPDATE-001` (всегда отдельно) |
| **AR** | API Requirement, требование к API: операция и правила API | `AR-001` | `AR-COUNTRY-001` | `AR-COUNTRY-LIST-001` |
| **EI** | External Interface, интерфейс с внешней системой | `EI-001` | `EI-COUNTRY-001` | нет |
| **SR** | System Requirement, среда, ОС, браузеры | `SR-001` | нет | нет |
| **UI** | User Interface, описание экрана или диалога с макетом | `UI-G-TOAST-001` (в глобальной SF) | `UI-COUNTRY-001` (экран общий для нескольких SF) | `UI-COUNTRY-LIST-001` |
| **AC** | Acceptance Criterion, сценарий приёмки (Gherkin) | `AC-G-PAG-001` | `AC-COUNTRY-001` (сквозная проверка UC) | `AC-COUNTRY-CREATE-001` |

## Уровни требований {#levels}

Требования образуют иерархию из трёх уровней: продукт (глобальный уровень), основная функциональность (F) и детальная 
функциональность (SF). Каждое требование записывается на самом нижнем уровне, на котором оно истинно целиком: относится 
к одной SF — на уровне SF, к нескольким SF одной F — на уровне F, к нескольким F — на глобальном уровне. Схема ниже 
показывает, какие типы требований допустимы на каждом уровне, а список под ней описывает каждый вид требований.

```
ПРОДУКТ (глобальный уровень)
 ├─ Глобальные требования: BG, CON, BR, NFR, DR, AR, EI, SR     BR-028, NFR-001
 ├─ Глобальные детальные функциональности (SF-G-…)               SF-G-PAG, SF-G-SORT, SF-G-FILTER, SF-G-TOAST
 │    └─ их FR, UI, AC                                           FR-G-PAG-001
 │
 └─ ОСНОВНАЯ ФУНКЦИОНАЛЬНОСТЬ  F-…  =  СПЕЦИФИКАЦИЯ  SPEC-…      F-COUNTRY
      │   Требования уровня F: BR, NFR, DR, AR, EI, CON, UC, FR, UI, AC
      └─ ДЕТАЛЬНАЯ ФУНКЦИОНАЛЬНОСТЬ  SF-…                         SF-COUNTRY-CREATE
            Требования уровня SF: FR, DR, AR, UI, AC (BR и NFR как правило встраиваются)
```

- **Бизнес-цель (Business Goal, BG)**: Зачем бизнесу нужен продукт: цель, ради которой создаются функциональности. 
Записывается только на глобальном уровне. Основная функциональность ссылается на свои цели атрибутом `Цели` в паспорте.

- **Проектное ограничение (Constraint, CON)**: Ограничение, которое проект принимает как данность и в рамках которого 
создаётся продукт. Записывается на глобальном уровне. На уровне F допускается только если ограничение касается одной 
функциональности (например, внешней системы), на уровне SF не бывает.

- **Бизнес-правило (Business Rule, BR)**: Правило предметной области, которому подчиняются продукт и его данные. 
Записывается на глобальном уровне и на уровне F. На уровне SF встраивается в FR как условие.

- **Основная функциональность (F, Feature)**: Функциональность продукта, которую заказчик принимает целиком 
(«Справочник стран», «Накладные»). Не «Удаление страны» (отдельно не примет), а «Управление справочником стран».

- **Детальная функциональность (SF, Sub-Feature)**: Часть основной функциональности со своим поведением, которое можно 
описать и проверить отдельно (создание, импорт, список). Приоритет и статус каждой SF можно задать отдельно (импорт 
`should`, остальное `must`) - заказчик может принять на промежуточных этапах целиком одну или несколько SF.

- **Глобальная детальная функциональность (SF-G-…)**: SF, которая применяется во многих F (пагинация, тосты, формат 
ошибок, блокировка). У неё нет предметного родителя, поэтому код основной функциональности зарезервирован как `G`.

- **Сценарий (Use Case, UC)**: Зачем пользователь это делает: цель, шаги, альтернативы. Принадлежит F и ссылается на SF, 
которые использует. UC уровня SF не бывает. Один UC может использовать несколько SF, одна SF — быть в нескольких UC.

- **Функциональное требование (FR, Functional Requirement)**: Что делает система: «Система показывает список накладных 
выбранного направления». Проверяется через API и AC.

- **Нефункциональное требование (Non-Functional Requirement, NFR)**: Характеристика качества продукта. Записывается на 
глобальном уровне и на уровне F. На уровне SF встраивается в FR, а отдельным пунктом оформляется, только если у него 
есть собственный показатель и способ проверки (например, время ответа списка).

- **Требование к данным (Data Requirement, DR)**: Какие данные хранит система: состав полей сущности, типы, ограничения, 
уникальность. Поля записываются таблицей в одном месте, из неё строятся схема данных, таблицы БД и модели API. 
На уровне SF записывается всегда отдельным пунктом.

- **Требование к API (API Requirement, AR)**: Операция API с её атрибутами (метод и путь, роли, параметры, ответы) и 
общие правила API. Записывается на всех трёх уровнях: операция одной SF — на уровне SF, операция для нескольких SF и 
общие правила функциональности — на уровне F, правила для всех функциональностей — на глобальном уровне.

- **Внешний интерфейс (External Interface, EI)**: Как функциональность обменивается данными с внешней системой: что 
получает или отдаёт, протокол, порядок обмена, повторы, реакция на сбои. Записывается на глобальном уровне и на уровне 
F, на уровне SF не бывает.

- **Системное требование (System Requirement, SR)**: Среда, в которой работает продукт: операционная система, браузеры. 
Записывается только на глобальном уровне.

- **Интерфейсное требование (User Interface, UI)**:  Как это выглядит и работает на экране: вкладки, порядок, состояния. 
Каждый элемент ссылается на FR, который реализует. Если убрать интерфейс и оставить API, FR останется, а UI исчезнет.

- **Критерий приёмки (Acceptance Criterion, AC)**: Сценарий на языке Gherkin, по которому проверяют, что требование 
выполнено. Связывается с проверяемыми требованиями тегами (`@FR-…`, `@UC-…`, `@UI-…`, `@DR-…`). Записывается на всех 
трёх уровнях: сквозная проверка UC принадлежит уровню F, проверка одной SF — уровню SF, проверка глобальной SF — 
глобальному уровню.
