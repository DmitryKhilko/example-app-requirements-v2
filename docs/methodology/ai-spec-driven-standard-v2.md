# Адаптированный стандарт создания требований для ИИ-разработки (Spec-Driven Development)

## 1. Назначение и принципы стандарта

Данный документ описывает оптимизированный стандарт ведения функциональных и технических требований при разработке ПО
короткими спринтами с активным использованием ИИ-агентов (Cursor, Copilot, LLM) и сдачей результатов Заказчику.

Главный принцип: **Единый источник истины (Single Source of Truth)**. Мы отказываемся от расщепления одного требования
по множеству мелких артефактов (14 типов в классическом стандарте) и укрупняем документацию вокруг 7 базовых сущностей
(`F`, `SF`, `UC`, `DR`, `FR`, `AR`, `AC`) с точечным вынесением `UI` и `NFR`, а также поддержкой глобальных
функциональностей (`SF-G-*`).

---

## 2. Иерархия и оптимизация типов требований

Из исходного стандарта исключены как самостоятельные документы: `BG`, `CON`, `BR`, `EI`, `SR`. Их содержание влито в
оставшиеся артефакты, чтобы исключить дублирование и рассинхронизацию контекста для нейросетей.

| Префикс | Уровень | Назначение и что влито внутрь |
| :--- | :--- | :--- |
| **F** | Основная фича | Границы модуля, принимаемого Заказчиком целиком (`F-COUNTRY`). Включает реестр `SF` с приоритетами (`must`/`should`). |
| **SF-G** | Глобальный | Сквозные детальные функциональности (`SF-G-PAG`, `SF-G-LOCK`, `SF-G-TOAST`), содержащие свои `FR`, `AR`, `UI`, `AC`. |
| **SF** | Детальная фича | Самодостаточная единица разработки (`SF-COUNTRY-CREATE`). Объединяет внутри себя `FR`, `AR`, `AC` (и `UI`, если экран один). |
| **UC** | Уровень F | Сценарии использования для Заказчика и QA (`UC-COUNTRY-001`). Влиты бизнес-цели (`BG`). Пишутся строго без привязки к UI. |
| **DR** | Уровень F | Модель данных (`DR-COUNTRY`). Влиты бизнес-правила (`BR`) по уникальности, статусам и формату аудита. |
| **FR** | Внутри SF | Логика работы, валидации, права, алгоритмы. Влиты правила (`BR`), внешние интерфейсы (`EI`) и простой UI. |
| **AR** | Внутри SF | Контракт API: метод, путь, заголовки, JSON-схемы запросов и ответов, коды ошибок. Влиты ограничения (`CON`). |
| **AC** | Внутри SF | Критерии приёмки в формате Gherkin. Влиты проверяемые метрики качества (`NFR`). |
| **UI** | Уровень F (опц.) | Выносится в отдельный файл (`UI-COUNTRY`), только если один экран объединяет сразу несколько `SF`. |
| **NFR** | Уровень F (опц.) | Выносится отдельно (`NFR-COUNTRY`), только для сквозных метрик (производительность, сроки хранения логов). |

## 3. Структура файлов в репозитории

Документация хранится рядом с кодом в виде Markdown-файлов. Для каждой основной функциональности (`F-*`) создаётся
отдельная директория, а сквозные правила проекта выносятся в глобальную папку `_global/`:

```text
docs/
├── _global/                   # Глобальный контекст проекта для ИИ
│   ├── UI-KIT.md              # Ссылка на дизайн-систему и правила верстки
│   ├── SF-G-PAG.md            # Глобальная пагинация (FR + AR + UI + AC)
│   ├── SF-G-LOCK.md           # Глобальная оптимистичная блокировка (FR + AR + AC)
│   └── SF-G-ERRORS.md         # Единый формат ошибок API и тостов
└── F-COUNTRY/                 # Основная функциональность «Справочник стран»
    ├── INDEX.md               # Описание F-COUNTRY и реестр SF с приоритетами
    ├── UC-COUNTRY.md          # Сценарии использования (для Заказчика и ПМИ)
    ├── DR-COUNTRY.md          # Таблицы БД, индексы, статусы, аудит (+ диаграммы)
    ├── UI-COUNTRY.md          # Компоновка общих экранов (+ схема User Flow)
    ├── NFR-COUNTRY.md         # Сквозные NFR (время ответа, хранение логов 12 мес.)
    ├── SF-COUNTRY-LIST.md     # Спецификация списка и поиска (FR + AR + AC)
    ├── SF-COUNTRY-CRUD.md     # Спецификация карточки: чтение, правка, статус, удаление
    └── SF-COUNTRY-IMPORT.md   # Спецификация импорта из НСИ АСФР (FR + AR + AC)
```

## 4. Правила оформления артефактов

### 4.1. Глобальные функциональности (SF-G-*)
Сквозные механизмы (пагинация, сортировка, блокировки по версиям, формат сообщений) оформляются по тем же правилам,
что и обычные `SF`, но с префиксом `G` (`SF-G-LOCK`). В прикладных спецификациях (`SF-COUNTRY-*`) запрещено
дублировать их логику — достаточно указать ссылку на идентификатор (например, `Применяется правило SF-G-LOCK`).

### 4.2. Сценарии использования (UC-*)
* Описывают цель актора и диалог «Намерение — Реакция» по принципу «чёрного ящика».
* **Запрещено** указывать конкретные веб-элементы (кнопки, чекбоксы), числа пагинации (20 записей) и коды сообщений
  (`MSG:...`). Все детали реализации живут внутри `SF-*` и `UI-*`.
* Используются для согласования бизнес-логики с Заказчиком и формирования Программы и методики испытаний (ПМИ).

### 4.3. Требования к данным (DR-*)
* Оформляются в виде единой таблицы атрибутов сущности с указанием типов БД, обязательности и значений по умолчанию.
* Содержат правила уникальности (включая частичные индексы для логического удаления) и формат таблиц журнала аудита.

### 4.4. Детальные функциональности (SF-*)
Каждая `SF` — это самодостаточный контракт на разработку, состоящий из трёх обязательных блоков:
1. **FR (Функциональные требования):** Пошаговая логика обработки, проверка прав, таблица валидации полей, правила
   транзакций и фиксации аудита.
2. **AR (Требования к API):** Точный HTTP-метод, URL, примеры JSON для `Request` и `Response`, перечень кодов ошибок.
3. **AC (Критерии приёмки):** Сценарии в синтаксисе Gherkin (`Given / When / Then`), покрывающие позитивный путь и
   ключевые ошибки.

### 4.5. Размещение схем и диаграмм (Mermaid)
Отдельный тип требований для диаграмм не вводится. Схемы размещаются текстом на языке Mermaid внутри профильных файлов:
* **ER-диаграммы и машины состояний (`stateDiagram-v2`):** Внутри файла `DR-*.md` рядом с описанием таблиц и статусов.
* **Диаграммы последовательности (`sequenceDiagram`):** Внутри сложных `SF-*.md` (асинхронные процессы, интеграции).
* **Карты переходов экранов (`flowchart TD`):** В начале файла `UI-*.md` для фиксации роутинга и модальных окон.

## 5. Пайплайн ИИ-кодогенерации (Слои контекста)

Чтобы ИИ-агент генерировал код без галлюцинаций, контекст подаётся **тремя последовательными слоями** — от
бизнес-смысла к техническим контрактам и визуальному оформлению.

### Слой 1. Поведение и границы (`F` + `UC`)
* **Что передаём ИИ:** `INDEX.md` (описание `F`) и `UC-*.md`.
* **Что получаем:** Понимание бизнес-контекста, пользовательских потоков, краевых случаев и сквозной навигации.

### Слой 2. Контракты и логика (`DR` + `SF-G` + `SF` [`FR` + `AR` + `AC`] + `NFR`)
* **Что передаём ИИ:** Таблицы данных (`DR`), релевантные глобальные правила (`SF-G-*`), конкретную спецификацию
  (`SF-*`)
  и сквозные ограничения (`NFR`).
* **Что получаем:** Точные контракты БД, API, валидаций и автотестов без додумывания деталей.

### Слой 3. Визуал и компоненты (`UI` + `UI-KIT`)
* **Что передаём ИИ:** Описание экрана (`UI-*` или вшитый в `SF` блок) и глобальный гайд по дизайн-системе
  (`UI-KIT.md`).
* **Что получаем:** Готовый интерфейс на базе штатных компонентов проекта без изобретения собственной верстки.

### Матрица генерации артефактов кода по этапам

| Этап разработки | Входной контекст для ИИ | Результат генерации ИИ-агентом |
| :--- | :--- | :--- |
| **1. Проектирование БД** | `DR-*.md` + `NFR-*.md` | SQL-миграции, индексы (в т.ч. частичные), ORM-модели, таблицы аудита. |
| **2. Бэкенд и API** | `DR-*.md` + `SF-*.md` (`FR` + `AR`) + `SF-G-*.md` | Контроллеры, DTO, сервисный слой с валидацией, OpenAPI-схема, запись аудита. |
| **3. Фронтенд (UI)** | `UC-*.md` + `UI-*.md` + `SF-*.md` + `SF-G-*.md` + `UI-KIT.md` | Роутинг, сторы состояния, страницы, модальные окна, формы и интеграция с API. |
| **4. Тестирование (QA)** | `UC-*.md` + `SF-*.md` (`AC` на Gherkin) | Интеграционные API-тесты и E2E-сценарии (Playwright/Cypress) для самопроверки. |
| **5. Документация** | `INDEX.md` (`F`) + `UC-*.md` + `UI-*.md` | Руководство пользователя и Программа и методика испытаний (ПМИ) для Заказчика. |
